# 任务 2：模式匹配 —— 朴素 / KMP / nextval

## 1. 实现总览

`src/match.cpp` 共实现 6 个函数，全部位于 `namespace dsaac`，声明见 `src/match.hpp`：

| 函数 | 作用 | 时间 | 空间 |
| --- | --- | --- | --- |
| `naiveMatch` | 朴素匹配，返回首次匹配下标 | O((n−m+1)·m) | O(1) |
| `getNext` | 求 0-based 前缀函数 `next[i] = pi(pattern[0..i])` | O(m) | O(m) |
| `kmpMatch` | 用 `next` 驱动的 KMP | O(n+m) | O(m) |
| `getNextVal` | 按题面公式求 `nextval`（**展示表**，供 `NEXTVAL` 输出） | O(m) | O(m) |
| `getNextValTable` | 与 0-based KMP 下标语义匹配的**跳转表** | O(m) | O(m) |
| `kmpMatchNextVal` | 用 `getNextValTable` 驱动的 KMP | O(n+m) | O(m) |

下标约定：主串、模式串、输出下标全部 **0-based**；`next[i]` 是 `pattern[0..i]` 的
最长真前缀=真后缀长度，`next[0] = 0`。这一约定与骨架给出的 `getNext` 完全一致
（骨架原样保留，未做改动）。

### 1.1 为什么 KMP 的主串指针不回退

朴素算法失配时把主串指针 `i` 拉回 `i-j+1`、模式串指针归零，**已经比过的字符又比一遍**，
这是 O(nm) 的来源。KMP 的关键观察是：失配发生在 `pattern[j]` 时，`text[i-j..i-1]`
已经和 `pattern[0..j-1]` 逐字相等。既然这段主串内容我们**已经知道**，就不必重新读，
只需找到一个最大的 `k < j`，使 `pattern[0..k-1]` 恰好等于这段已匹配内容的后缀
`pattern[j-k..j-1]`——这个 `k` 只依赖模式串自己，也就是 `next[j-1]`。

于是：

```cpp
while (j > 0 && text[i] != pattern[j]) j = next[j - 1];  // 只动 j，i 不动
```

`i` 在整趟扫描里单调加一，最多前进 n 次，所以**成功比较 ≤ n 次**（每次成功都让 `j`
加一）。失配比较分两类：`j > 0` 时每次至少让 `j` 减 1，而 `j` 只靠成功比较增长，
故这类失配也 ≤ n 次；`j = 0` 时每次 `i` 至多发生一次，同样 ≤ n 次。合计 ≤ 3n。

更常见的是把上界定成 2n——那是在"`j = 0` 失配很少"时的实际表现，不是严格结论。
后面 bench 的两条用例正好落在这一档：case A 为 380 001 次（≈1.9n，`j = 0` 处从未失配），
case B 为 800 020 次（≈2.0n）。无论哪个数，都与 n 同阶、不随 m 增长，这就是
"主串不回退 ⇒ O(n+m)"的完整论证。

## 2. Step 1：朴素算法的最坏情况

最坏输入是"每个起点都几乎匹配到末尾才失配"的串，例如

```text
text    = 'A'×200000 + 'B'      n = 200001
pattern = 'A'×20000  + 'B'      m = 20001
```

- 前 180 000 个起点都能一路匹配到 `pattern[m-1]` 的 `'B'` 才在最后一个字符失配，
  每个起点比较 m 次；
- 第 180 001 个起点（下标 180000）匹配成功，同样比较 m 次；
- 若没有成功，最后一个起点之后还会再试，但这里提前返回。

所以比较次数恰为 `(n−m+1)·m = 180 001 × 20 001 = 3 600 200 001`，
与 bench 实测**逐位相同**。朴素算法在这条用例上约 **1.48 s**（-O2）。

这个例子说明朴素算法的上界不是"平均 O(nm)"，而是**真的能取到** O((n−m+1)·m)：
只要模式串和主串的开头足够长地重复，每次滑窗都会重扫 m 个字符，
而每次滑窗只有 1 个字符是"新"信息。

朴素算法的空间复杂度是 **O(1)**（除输入本身只用三个 int），
`getNext`/`getNextVal` 才是 O(m)。这也是它唯一的优点：不需要任何预处理表。

## 3. Step 2：KMP 与朴素算法的差距

同一条用例上的实测（`make bench`，每种算法重复取最小值）：

| 算法 | 比较次数 | 耗时（多次运行区间） | 每次比较 |
| --- | --- | --- | --- |
| 朴素 | 3 600 200 001 | 1478 ~ 1487 ms | 0.41 ns |
| KMP | 380 001 | 0.551 ~ 0.564 ms | 1.45 ns |
| nextval 版 KMP | 380 001 | 0.543 ~ 0.550 ms | 1.43 ns |

（比较次数是程序的**精确计数**，每次运行完全相同；耗时是 4 次独立运行的最小值区间。
本机为共享云主机、`cpu MHz` 会在 1.3 ~ 2.6 GHz 之间浮动，所以耗时只用于比较数量级，
不当作绝对基准。）

**比较次数差 9 474 倍，耗时只差约 2 660 倍**——这个反差本身就是分析点：
两边的"一次比较"成本不一样。

- 朴素的内层是 `while (text[i+j] == pattern[j]) j++`，下标按 1 递增、访问的
  是相邻内存，硬件预取器能全程命中；分支在长重复段上几乎总是"相等"，预测器
  一次就学对。单次比较 ≈ 0.41 ns。注意这条循环**并没有被自动向量化**
  （`-fopt-info-vec-all` 报告 `unsupported control flow in loop`：循环出口
  依赖内层比较结果），所以 0.41 ns 已经是标量循环的吞吐水平，基本是
  每周期推进一个字符；
- KMP 每次失配要做 `j = next[j-1]`，下一条指令的地址依赖于刚读出的值，
  形成一条**串行 load-use 依赖链**，每步约 4~5 个周期，无法流水。单次比较 ≈ 1.45 ns。

为确认这一点不是猜测，我在 case A 上做了个对照实验：该用例里 `next[j-1]` 恰好
恒等于 `j-1`，于是可以写一个"比较次数完全相同、但不查表"的变体 `j = j - 1`。
两组轮转测量、第 1 轮热身、其后 19 轮取最小值，三次独立运行结果稳定：

```text
kmpMatch（查 next[]）  0.552 ~ 0.562 ms
j = j - 1（不查表）     0.244 ms
比值                    2.26 ~ 2.30
```

**2.3 倍的差距全部来自 `next[]` 的依赖加载**，与分支预测无关——两条循环的
分支形态完全一样，唯一的区别是跳转目标是"刚读出来的内存值"还是"算术结果"。
这也解释了为什么连跑一次 `probe` 会出现 8.2 倍这种异常值：不轮转、不预热时，
先跑的那组要独自承担几 MB 数据结构的首次触页成本（任务 1 里遇到过的同一个坑）。

也就是说，KMP 用"更少的比较、更贵的比较"换掉了"更多但更便宜的比较"。
当 n、m 再大一两个数量级时，这个常数差会被 O(nm) 的增长彻底淹没；
如果只用小样例（n、m 几十），两者耗时可能都在微秒级，反而看不出 KMP 的优势——
这也是为什么 Step 1 要求专门构造极端用例。

具体到这条用例还能逐项对账：前 20 000 个字符各成功 1 次；之后 180 000 个字符
每个都是"在 `pattern[20000]='B'` 处失配 1 次（退回 `j=19999`）→ 与 `'A'` 成功 1 次"，
共 360 000 次；最后主串的 `'B'` 成功一次即完成匹配。合计
`20 000 + 360 000 + 1 = 380 001`，与实测逐位相同。

## 4. Step 3：nextval 的收益

### 4.1 原始的 next 浪费在哪

`next[j-1]` 只保证"前缀=已匹配后缀"，没有检查**回退后要比较的那个字符**。
若 `pattern[j] == pattern[next[j-1]]`，那么 `text[i] != pattern[j]` 已经成立，
退过去再比 `text[i]` 与 `pattern[next[j-1]]` 必然**再失配一次**——这一次比较是纯浪费。

以 `pattern = 'A'×20000 + 'B'` 为例，`next` 形如 `0 1 2 3 …`：在第 `j` 位失配时
退到 `j-1`，而 `pattern[j-1]` 仍是 `'A'`，与刚失配的 `'A'` 相同，于是继续退……
一路退到 0 才停。`nextval` 把这一整段相同字符直接压成一次跳转。

### 4.2 能体现差别的用例

```text
text    = ('A'×20000 + 'C') × 20     n = 400020
pattern = 'A'×20000 + 'B'            m = 20001
```

每个块末尾都是 `'C'`，与模式串末尾的 `'B'` 失配。这 20 个失配点上：

- `next` 每退一格还要拿 `'A'` 跟 `'C'` 比一次（必然失败），于是每个块白白多付出
  约 2 万次无效比较；
- `nextval` 一步退到位，直接重新对齐下一段 `'A'`。

| 算法 | 比较次数 | 耗时（多次运行区间） |
| --- | --- | --- |
| 朴素 | 3 800 590 020 | 1486 ~ 1514 ms |
| KMP | 800 020 | 1.313 ~ 1.344 ms |
| nextval 版 KMP | 400 060 | 0.466 ~ 0.467 ms |

（朴素那行的数字可手算验证。`n−m+1 = 380 020` 个起点，按块内偏移 `o` 分类：
`o = 0` 的起点能比完 20 000 个 `'A'`、在末尾 `'C'` vs `'B'` 失配，共 20 001 次；
`o > 0` 的起点先命中 `20 000−o` 个 `'A'`，再在 `'C'` vs `'A'` 失配，共
`20 001−o` 次。前 19 个块是完整的，各贡献
`20 001 + Σ_{o=1}^{20000}(20 001−o) = 200 030 001`；第 20 块只覆盖到一个
`o = 0` 起点，贡献 20 001。合计 `19 × 200 030 001 + 20 001 = 3 800 590 020`，
与计数版实测逐位相同。）

nextval 把比较次数**降到约一半**（800 020 → 400 060，比值 2.00），耗时改善却接近 2.9 倍。
原因仍是每次比较的成本不同：被消掉的 399 960 次全是"读 `next[k]` → 跳转 →
立刻失配"的串行依赖步（每步约 4~5 个周期），而留下来的 400 060 次里有 400 000 次
是按顺序匹配成功的廉价比较，单次成本差了一个数量级。

拆开看每个块（20 000 个 `'A'` 全部匹配成功 = 20 000 次廉价比较，剩下是块尾失配的处理）：

| 每块 | 成功比较 | 失配处理 | 合计 |
| --- | --- | --- | --- |
| KMP | 20 000 | 20 001 | 40 001 |
| nextval | 20 000 | 3 | 20 003 |

KMP 的 20 001 次失配处理是：`'C'` 与 `pattern[20000]='B'` 比一次，然后沿 `next`
一格一格退（`next[19999]=19999`、`next[19998]=19998`、…）；这些位置上的字符全是
`'A'`，每退一格就多比一次 `'A'` vs `'C'`，一直退到 `j=0` 再比一次，共
`1 + 19 999 + 1 = 20 001` 次。

nextval 的 3 次则来自：① 在 `j=20000` 比 `'B'` vs `'C'`；② 中间落到 `j=19999`
比一次 `'A'` vs `'C'`；③ 归零后在 `j=0` 再比一次。

下界其实是 2 次（"在模式串末尾失配" + "归零后再失配"，这两次无法避免），多出来的
第 ② 次是**结构性残留**：`pattern[20000]='B'` 与 `k = next[19999] = 19999` 处的
`'A'` 不同，所以跳转表 `nv[20000]` 只能取 19999 而不能直接取 0，必须多落一步，
再靠 `nv[19999]=0` 归零。即便如此，每块的失配处理已从 20 001 次降到 3 次
（消去 19 998 次，99.985%）；20 个块合计 800 020 → 400 060。

注意这里的复杂度量级没变，两边都是 O(n+m)；nextval 优化的是**常数因子**，
并且只在模式串含成段相同字符时才有收益。若模式串没有重复片段（如 `abcde`），
`nextval == next`，两者比较次数完全相同。

### 4.3 `nextval` 的两张表：展示表 vs 跳转表

这是本任务实现中唯一需要单独说明的地方。题面给出的 `getNextVal` 公式是：

```text
k = nextval[i]（此时尚未改写，等于 next[i]）
若 k == i            → nextval[i] = 0
否则若 p[i] == p[k]  → nextval[i] = nextval[k]
否则                 → nextval[i] = k
```

按此公式 `"AAAAB"` 得到 `0 0 0 0 0`（与题面自检要求一致），`NEXTVAL` 操作输出的
就是这张**展示表**。但它**不能直接当 0-based KMP 的跳转表**用：

- KMP 中 `j` 表示"已匹配长度"，在 `pattern[j]` 处失配时应退到 `next[j-1]`，
  优化的目标也应是 `k = next[j-1]`，而上述公式取的是 `k = next[i]`，下标错了一位；
- 它还把"连续相同字符"一律压到 0，丢掉了"已经匹配了 4 个 A 因此不必退回开头"的信息。
  拿它去跑题面自检样例 `AAAAAAAAAAB` / `AAAAB` 会返回 **−1**（正确答案 6）。

因此实现里把它拆成两个函数：

- `getNextVal` —— 严格按题面公式，只用于 `NEXTVAL` 展示；
- `getNextValTable` —— 按下标语义修正为 `k = next[j-1]`，
  `pattern[j] == pattern[k]` 时 `nv[j] = nv[k]`，否则 `nv[j] = k`，`nv[0] = 0`。
  对 `"AAAAB"` 得到 `0 0 0 0 3`（末位保留 3，失配时不必退回开头）；
- `kmpMatchNextVal` —— 用跳转表驱动，失配时 `j = nv[j]`（**不是** `nv[j-1]`）。

`KMP_NEXTVAL` 与 `NAIVE`、`KMP` 在全部样例与穷举测试中结果完全一致；
展示表与跳转表的差别只出现在 `NEXTVAL` 的输出里，不影响任何匹配结果。

> 穷举验证：字母表 `{A,B}`、主串长 ≤ 8、模式串长 ≤ 5 的全部组合共 32 193 例，
> `kmpMatch` 与 `kmpMatchNextVal` 均与朴素算法逐一相同（0 例不一致）。反过来，
> 若强行用展示表驱动 KMP（`j = nv[j-1]` 或 `j = nv[j]`），分别有 610 与 1 854 例
> 算出错误下标，说明这个拆分不是多余的。扩大到"主串 ≤ 8 / 模式串 ≤ 8"
> （261 121 例）以及"主串 ≤ 10 / 模式串 ≤ 5"（128 961 例），结论不变。

`PERF <name> n=<主串长度> m=<模式串长度> time_ms=<毫秒>`，例如题面样例：

```text
PERF naive n=11 m=5 time_ms=0.001
PERF kmp n=11 m=5 time_ms=0.001
PERF kmp_nextval n=11 m=5 time_ms=0.001
```

驱动里每种算法只运行一次（题目要求"各计时一次"），因此小样例上的数字只有
微秒级、且会抖动；要观察算法差异应以 `make bench` 的重复取最小值结果为准——
这和任务 1 里"预热 + 取最小值"的理由相同：单次测量会把缺页、频率调节等
一次性开销算进去。

内存安全另用 `-fsanitize=address,undefined` 把 11 个样例和若干畸形输入
（字段缺失、操作名拼错）各跑一遍，无报错、无泄漏。畸形输入走的是
`input_util.h` 的错误通道：stderr 打印 `输入错误：…`，退出码 1，不产生任何
功能输出。

## 7. 结论

1. 朴素算法在"长重复前缀 + 末尾失配"的输入上确实取到 O((n−m+1)·m) 上界，
   本机 3.6×10⁹ 次比较、约 1.5 s；
2. KMP 靠"失配只回退模式串、主串指针不回退"把比较次数压到 O(n)，
   同例 38 万次比较、0.55 ms；两者比较次数差近万倍，耗时差约 2.7 千倍，
   差额来自 KMP 单次比较的常数更大（`next[]` 的串行依赖加载）；
3. nextval 只消掉"回退后必然再失配"的冗余比较，在成段相同字符的模式串上
   把比较次数减半，复杂度量级不变，属于常数级优化；
4. 题面给的 `nextval` 公式得到的是展示表，不能直接驱动 0-based KMP；
   实现中把"展示表"和"跳转表"分开，`NEXTVAL` 输出前者，匹配使用后者，
   匹配结果与朴素、KMP 在穷举测试中完全一致。
